# Test Specification

> **⚠️ WARNING — `surface.json` is stale and was NOT used as the route source.**
> `.pipeline/surface.json` still contains the untouched scaffold contract (`GET /health`,
> `GET /trpc/users.findAll`, `GET /trpc/users.findById`, components `app-root` / `app-home`,
> testIds `users-list` / `user-item-{id}`). None of those routes exist in the StockRoom spec —
> the tRPC layer is explicitly deleted by `backend_agent`. The API surface below is therefore
> derived from the approved spec plus the surface contract table in `.pipeline/tasks.md`
> (19 REST endpoints under the `/api` prefix). **`surface.json` must be regenerated by the
> implementing agents before the pipeline declares success**; a test run that still finds
> `/trpc/*` routes is a failure, not a pass.
>
> Two further scaffold/spec conflicts that tests must pin down:
> - `colossus.yaml` declares `projectName: frontend`, `outputDir: dist/frontend/browser`, backend `port: 3001`; the spec requires Angular project `stockroom`, output `dist/stockroom/browser`, backend `3000`. Whichever wins, `frontend/Dockerfile`, `angular.json`, `nginx.conf` and `colossus.yaml` must agree — see DI-10.
> - `.colossus-acceptance.json` sets `ready_testid: "app-ready"` with `reject_signatures` `home-title">Users<`, `Loading...`, `Failed to load users.` The shell must keep `data-testid="app-ready"` and must never render those strings — see J-13.
>
> **Role vocabulary.** The spec says `clerk` / `manager`; `tasks.md` implements `enum UserRole { ADMIN MANAGER CLERK USER }` with `ADMIN` as the manager superset. Tests below use **manager-level** to mean "role that passes the manager gate" (`ADMIN` or `MANAGER`) and **clerk** to mean `CLERK`. Every manager-gated assertion must also be run with a `USER`-role token if that role is ever assignable (expect 403).

### Shared fixtures
All API cases assume a DB seeded per `prisma/seed.ts` and these actors:
- `MGR` — manager-level token (`manager@demo` / `Demo1234!`)
- `CLK` — clerk token (`clerk@demo` / `Demo1234!`)
- `ANON` — no `Authorization` header
- `BAD` — `Authorization: Bearer not.a.jwt`
- `EXP` — a structurally valid HS256 token with `exp` in the past
- Locations `LOC_A` (`Zone A`), `LOC_B` (`Zone B`), `LOC_C` (`Zone C`)
- `ITEM_X` — a fixture item created per-suite with a unique SKU and `reorderAt: 10`, starting at 0 on hand

## API tests

### `GET /api/health`
- **Happy path**: `API-HLT-01` — `ANON` → `200`, body `{ status: "ok" }` (object with a truthy status field; no DB round-trip required).
- **Validation failures**: n/a — no inputs.
- **Auth failures**: `API-HLT-02` — endpoint is `@Public()`; `ANON` must NOT get `401`. `API-HLT-03` — `BAD` (malformed bearer token) still returns `200`, proving the global `JwtAuthGuard` is bypassed rather than merely lenient.
- **Idempotency / edge cases**: `API-HLT-04` — 5 sequential calls all return `200` with identical body shape; response time budget < 500 ms (no DB dependency).

### `GET /api/health/deep`
- **Happy path**: `API-HLT-05` — `ANON` with Postgres up → `200`, body reports database reachable (e.g. `{ status: "ok", database: "up" }`), produced by an actual `SELECT 1`.
- **Validation failures**: n/a.
- **Auth failures**: `API-HLT-06` — `ANON` → not `401` (public).
- **Idempotency / edge cases**: `API-HLT-07` — with Postgres stopped/unreachable (`DATABASE_URL` pointed at a dead port), returns `503` (or `500`) and a non-`ok` status — it must NOT return `200`, otherwise the compose healthcheck is meaningless. `API-HLT-08` — response body must never leak `DATABASE_URL`, password, or a raw driver stack trace.

### `POST /api/auth/signup`
- **Happy path**: `API-SGN-01` — on a **fresh, unseeded** DB, `{ email: "first@x.io", password: "Str0ng!pass" }` → `201`/`200` with `{ token, user: { id, email, role } }` where `role` is manager-level (`ADMIN`); the token decodes to that user. `API-SGN-02` — a second signup on the same DB → user `role === "CLERK"`. `API-SGN-03` — against the **seeded** DB (seed runs first), any signup → `role === "CLERK"`, never manager. `API-SGN-04` — the returned token is immediately usable: `GET /api/auth/me` with it → `200`.
- **Validation failures**: `API-SGN-05` — missing `email` → `400`. `API-SGN-06` — `email: "not-an-email"` → `400` with a field-level message naming `email`. `API-SGN-07` — missing or empty `password` → `400`. `API-SGN-08` — extra unknown property `{ role: "ADMIN" }` in the body is stripped by `ValidationPipe({ whitelist: true })` — request either `400`s or succeeds with `role === "CLERK"`; **privilege escalation via body must be impossible**. `API-SGN-09` — `qty`-style type confusion: `password: 12345` (non-string) → `400`.
- **Auth failures**: `API-SGN-10` — endpoint is `@Public()`; `ANON` must reach it (not `401`).
- **Idempotency / edge cases**: `API-SGN-11` — signing up with an already-registered email (`manager@demo`) → `409` (or `400`) and `SELECT count(*) FROM "User"` is unchanged. `API-SGN-12` — the response body (and `GET /api/auth/me`) never contains `passwordHash` or `password`. `API-SGN-13` — the stored `passwordHash` is a bcrypt hash (`$2[aby]$10$…`, cost 10) and is not the plaintext.

### `POST /api/auth/login`
- **Happy path**: `API-LGN-01` — `{ email: "manager@demo", password: "Demo1234!" }` → `200` `{ token, user: { id, email, role } }` with manager-level role. `API-LGN-02` — same for `clerk@demo` → `role === "CLERK"`. `API-LGN-03` — decoded JWT header `alg === "HS256"`, payload carries the user id/email/role and an `exp` ≈ 24 h out (within ±5 min).
- **Validation failures**: `API-LGN-04` — empty body `{}` → `400`. `API-LGN-05` — `email: "nope"` (malformed) → `400`.
- **Auth failures**: `API-LGN-06` — correct email, wrong password → `401`. `API-LGN-07` — unknown email → `401`. `API-LGN-08` — the `401` message is identical for cases 06 and 07 (no user-enumeration oracle) and never states "user not found".
- **Idempotency / edge cases**: `API-LGN-09` — two logins in a row both return usable tokens (no server-side session invalidating the first); logout is client-side only. `API-LGN-10` — a token signed with a different `JWT_SECRET` is rejected `401` on a protected endpoint.

### `GET /api/auth/me`

- **Auth failures**: `API-ME-03` — `ANON` → `401`. `API-ME-04` — `BAD` → `401`. `API-ME-05` — `EXP` (expired token) → `401`.
- **Idempotency / edge cases**: `API-ME-06` — response never includes `passwordHash`. `API-ME-07` — header `Authorization: Demo1234!` (no `Bearer ` scheme) → `401`.

### `GET /api/items`
- **Happy path**: `API-ITL-01` — `CLK` → `200`, array where each element has `id, sku, name, description, unit, reorderAt, totalQty`. `API-ITL-02` — `MGR` → `200`, same shape (list is not manager-gated). `API-ITL-03` — for a fixture item with stock 20 in `LOC_A` and 10 in `LOC_B`, its `totalQty === 30` (sum across locations, not per-row duplication). `API-ITL-04` — an item with no `StockLevel` rows returns `totalQty === 0`, not `null`/absent. `API-ITL-05` — seeded DB returns exactly 8 items.
- **Validation failures**: `API-ITL-06` — unknown query params (`?bogus=1`) are ignored, still `200`.

- **Idempotency / edge cases**: `API-ITL-09` — repeated `GET` returns a stable list; no item is duplicated once it has stock in 2+ locations (guards against a join that fans out rows).

### `GET /api/items/:id`
- **Happy path**: `API-ITD-01` — `CLK` with a valid id → `200` item plus `stockLevels[]`, each entry `{ locationId, location: { name, zone }, qty }`. `API-ITD-02` — **`sum(stockLevels[].qty) === totalQty`** for a fixture item stocked 20/`LOC_A` + 10/`LOC_B` → `totalQty === 30`, `stockLevels.length === 2`.
- **Validation failures**: `API-ITD-03` — non-existent but well-formed id → `404`. `API-ITD-04` — malformed id (e.g. `abc` where a cuid/uuid is expected) → `400` or `404`, never a `500` Prisma leak.
- **Auth failures**: `API-ITD-05` — `ANON` → `401`.
- **Idempotency / edge cases**: `API-ITD-06` — item with zero stock returns `stockLevels: []` and `totalQty: 0` (empty array, not `null`). `API-ITD-07` — a location whose stock fell to 0 via `OUT` either is absent or shows `qty: 0`; the sum invariant in `API-ITD-02` must still hold.

### `POST /api/movements`
- **Happy path**: `API-MVC-01` — **IN**: `CLK` posts `{ type: "IN", itemId: ITEM_X, toLocId: LOC_A, qty: 50 }` → `201`; `GET /api/items/:id` shows `LOC_A` `qty: 50`, `totalQty: 50`; **and** a matching `Movement` audit row exists with the clerk's `userId` and a `createdAt`. `API-MVC-02` — **OUT**: then `{ type: "OUT", itemId, fromLocId: LOC_A, qty: 20 }` → `201`; balance is `30`. `API-MVC-03` — **TRANSFER**: then `{ type: "TRANSFER", itemId, fromLocId: LOC_A, toLocId: LOC_B, qty: 10 }` → `201`; `LOC_A === 20`, `LOC_B === 10`, **`totalQty` still 30** (transfer conserves total). `API-MVC-04` — `MGR` may also post movements (not clerk-exclusive). `API-MVC-05` — optional `note` is persisted and returned in the log. `API-MVC-06` — `IN` to a location with **no existing `StockLevel` row** creates it via upsert → `qty` equals the posted amount (first-time-credit path).
- **Validation failures**: `API-MVC-07` — `IN` without `toLocId` → `400`. `API-MVC-08` — `OUT` without `fromLocId` → `400`. `API-MVC-09` — `TRANSFER` missing `toLocId` → `400`; `API-MVC-10` — `TRANSFER` missing `fromLocId` → `400`. `API-MVC-11` — `TRANSFER` with `fromLocId === toLocId` → `400` (must differ). `API-MVC-12` — `qty: 0` → `400`; `API-MVC-13` — `qty: -5` → `400`; `API-MVC-14` — `qty: 2.5` → `400` (positive **integer**). `API-MVC-15` — `type: "ADJUST"` (not in the enum) → `400`. `API-MVC-16` — unknown `itemId` → `400`/`404`. `API-MVC-17` — unknown `fromLocId`/`toLocId` → `400`/`404`, never a `500`. `API-MVC-18` — `IN` that also supplies `fromLocId` is either rejected `400` or the stray field is whitelisted away and no debit occurs — assert no unintended debit either way.
- **Auth failures**: `API-MVC-19` — `ANON` → `401`. `API-MVC-20` — `BAD` → `401`.
- **Idempotency / edge cases**: `API-MVC-21` — **insufficient stock**: with 5 on hand in `LOC_A`, `OUT qty: 10` → `400` with message `insufficient stock`, **and** a re-read shows the stored balance is still exactly `5`, **and** no `Movement` row was written (whole transaction rolled back). `API-MVC-22` — `OUT` from a location where the item has no `StockLevel` row at all → `400` insufficient stock (the conditional `updateMany` matches 0 rows), no row created. `API-MVC-23` — `TRANSFER` whose source is short → `400`, and **neither** side moved: source unchanged, destination unchanged (no partial credit). `API-MVC-24` — `OUT` of exactly the on-hand quantity (5 of 5) → `201`, balance lands on `0`, never negative. `API-MVC-25` — **CONCURRENCY REGRESSION FENCE**: with 10 on hand, fire N=5 parallel `OUT qty: 10` requests; assert exactly **one** returns `201`, four return `400`, final balance is exactly `0`, never negative at any read, and exactly one `Movement` row was created. (This is the guard against the conditional-`updateMany` being refactored into a read-then-write.) `API-MVC-26` — two parallel first-time `IN`s to the same `(itemId, locationId)` (the `P2002` upsert race): both succeed after the single retry, final `qty` equals the sum, exactly one `StockLevel` row exists.

- **Auth failures**: `API-MVL-07` — **`CLK` → `403`** (log is manager-only). `API-MVL-08` — `ANON` → `401`.

### `GET /api/reports/low-stock`
- **Happy path**: `API-LOW-01` — `MGR` → `200` array of `{ item fields…, totalQty, reorderAt }` (plus a shortfall value); sorted by shortfall (`reorderAt - totalQty`) descending.
- **Validation failures**: `API-LOW-02` — `?sort=bogus` → `400` or falls back to the default order (assert documented behaviour, not `500`).
- **Auth failures**: `API-LOW-03` — **`CLK` → `403`**. `API-LOW-04` — `ANON` → `401`.
- **Idempotency / edge cases**: `API-LOW-05` — **`<=` boundary, at reorder point**: item with `reorderAt: 10` and exactly `10` on hand **is present** (spec pins `totalQty <= reorderAt`). `API-LOW-06` — **below**: `reorderAt: 10`, 17 on hand, `OUT 5` → 12 on hand… still absent; a further `OUT 2` → 10 on hand → present. Explicitly per the spec scenario: `reorderAt: 10` with 12 on hand after an `OUT 5` from 17 appears once the balance reaches `<= 10`; assert the exact predicate rather than an off-by-one `<`. `API-LOW-07` — **above**: item with 40 on hand and `reorderAt: 10` is **absent**. `API-LOW-08` — item with `totalQty: 0` and `reorderAt: 10` is present with the largest shortfall (sorts first). `API-LOW-09` — the report aggregates **across locations**: 6 in `LOC_A` + 6 in `LOC_B` vs `reorderAt: 10` → `totalQty 12` → absent (not two per-location rows both flagged).

## UI / journey tests

### Journey: J-01 — Unauthenticated visitor is redirected to login and sees the brand
- **Steps**: Navigate directly to `/` with an empty `localStorage`.
- **Expected outcomes**: Redirected `/` → `/items` → `/login` (URL ends at `/login`); the literal text **`StockRoom`** is present in the rendered DOM; `document.title === "StockRoom"`; `[data-testid="app-ready"]` is in the DOM. Brand is rendered synchronously by the shell — never gated behind a spinner or an authenticated data fetch.
- **Negative path**: Deep-linking `/items`, `/items/<id>`, `/locations`, `/movements`, `/movements/new`, `/reports/low-stock`, `/admin/settings` while unauthenticated each redirects to `/login`; none flashes protected data first.

### Journey: J-02 — Clerk signs in and lands on the item list
- **Steps**: `/login` → type `clerk@demo` / `Demo1234!` → submit.
- **Expected outcomes**: Redirect to `/items`; the item table renders sku / name / unit / reorderAt / totalQty columns for the 8 seeded items; the token is persisted in `localStorage`; the header shows the clerk identity plus a logout control.
- **Negative path**: Wrong password → stays on `/login`, an inline server-error message is shown, no token is written, no redirect occurs. Submitting an empty form shows inline required-field errors and issues no HTTP request.

### Journey: J-03 — Manager signs in and sees role-gated navigation
- **Steps**: `/login` as `manager@demo` → submit → inspect header nav.
- **Expected outcomes**: Nav exposes Locations, Movement log and Low-stock links (and `/admin/settings` for an admin); each navigates to its route and loads without a 403 banner.
- **Negative path**: Signed in as the clerk, those manager-only nav links are absent; forcing the URL `/movements` or `/reports/low-stock` with a clerk token redirects away (to `/items`) or shows an access-denied view — never the manager data.

### Journey: J-04 — New user signs up
- **Steps**: `/login` → follow the signup link → `/signup` → enter a new email + password → submit.
- **Expected outcomes**: Account created, token stored, redirect to `/items`; the new user has the **clerk** role (seed ran first), so manager-only nav is hidden.
- **Negative path**: Reusing `manager@demo` shows the server's duplicate-email error inline without clearing the form; an invalid email or short password shows field-level validation before any request is sent.

### Journey: J-05 — Browse the catalogue and search/sort via the URL
- **Steps**: `/items` as clerk → type a SKU fragment into search → change sort.
- **Expected outcomes**: The URL becomes `/items?q=<fragment>&sort=<key>`; the table filters/reorders to match. Reloading that exact URL restores both the filter text and the sort with the same rows — state lives in query params, not buried component state.
- **Negative path**: A `q` matching nothing renders an explicit empty state (not a blank table or a spinner that never resolves); an API failure renders an error state.

### Journey: J-06 — Inspect an item's per-location breakdown
- **Steps**: `/items` → click an item row → lands on `/items/:id` → open the locations panel.
- **Expected outcomes**: URL is `/items/:id?panel=locations`; the header shows sku/name/unit/reorderAt; the per-location table lists each location and qty, and the **displayed rows sum to the displayed `totalQty`**. Loading `/items/:id?panel=locations` directly restores the open panel.
- **Negative path**: `/items/<nonexistent-id>` shows a not-found state, not a crash or an infinite spinner.

### Journey: J-07 — Manager creates and edits an item
- **Steps**: `/items?modal=create` (or click "New item") → fill sku/name/unit/reorderAt → save; then `/items/:id?modal=edit` → change the name → save.
- **Expected outcomes**: Modal state is restored on a direct load of `?modal=create` / `?modal=edit`; on save the modal closes, the URL drops the `modal` param, and the new/updated row appears in the list and persists across a reload.
- **Negative path**: Submitting a duplicate SKU keeps the modal open and shows the server's duplicate-SKU message inline against the `sku` field with no second row created; a clerk sees no create/edit controls at all, and force-loading `?modal=create` as a clerk cannot produce a successful write (the API 403 is surfaced, not swallowed).

### Journey: J-08 — Manager deletes an item and hits the restriction
- **Steps**: As manager open an item **with** movement history → trigger delete → confirm.
- **Expected outcomes**: The 409 is surfaced as an inline explanatory message ("item has stock or movement history"); the item remains in the list after a reload.
- **Negative path**: Deleting a brand-new item with no stock and no history succeeds, the row disappears, and navigating back to its `/items/:id` shows the not-found state.

### Journey: J-09 — Manager manages locations
- **Steps**: `/locations` as manager → open `?modal=create` → add `Zone D` → save → reopen an existing row via `?modal=edit&id=<id>` → rename → save → attempt to delete a referenced location.
- **Expected outcomes**: List shows name + zone; direct loads of `?modal=create` and `?modal=edit&id=<id>` restore the dialog with the right record prefilled; create/edit persist across reload.
- **Negative path**: Deleting a location holding stock shows the 409 message inline and the location stays; a clerk deep-linking `/locations` is redirected/denied.

### Journey: J-10 — Clerk records IN / OUT / TRANSFER movements
- **Steps**: `/movements/new?type=IN&itemId=<id>` as clerk → confirm the item is prefilled and only a **destination** selector is shown → qty 50 → submit. Repeat with `?type=OUT` (only a **source** selector) qty 20, and `?type=TRANSFER` (**both**, and the same location cannot be picked for both) qty 10.
- **Expected outcomes**: The type selector is bound to `?type=`; switching it updates the URL and swaps the location inputs; each submit shows a success confirmation, and `/items/:id` then reads `LOC_A 20` / `LOC_B 10` with `totalQty 30`. The location dropdowns are populated from `GET /api/locations` (which a clerk is allowed to call).
- **Negative path**: An `OUT` larger than the on-hand balance renders the backend's **`insufficient stock`** 400 inline **without clearing the form** (item, type, qty and location selections all survive), and re-reading the item shows the balance unchanged. Submitting `TRANSFER` with source === destination is blocked with a field-level message.

### Journey: J-11 — Manager filters the movement audit log
- **Steps**: `/movements` as manager → set the item filter → set a type → set a from/to date range → page forward.
- **Expected outcomes**: URL becomes `/movements?itemId=&type=&from=&to=&page=`; the table shows item, type, from/to location, qty, user, timestamp, note; rows are newest-first; only rows matching **all** active filters appear; paging changes `?page=` and yields a disjoint row set. Reloading the filtered URL restores every filter control and the same rows.
- **Negative path**: A filter combination with no matches shows an explicit "no movements" empty state; a clerk deep-linking `/movements` is redirected/denied.

### Journey: J-12 — Manager reads the low-stock report
- **Steps**: `/reports/low-stock` as manager; then toggle `?sort=`.
- **Expected outcomes**: Lists only items with `totalQty <= reorderAt`, with a shortfall column, ordered by shortfall; the seeded data makes this list **non-empty on first load**. `?sort=` is reflected in the URL and restored on reload. Recording an `OUT` that drops an item to its reorder point makes it appear on the next load; an `IN` that lifts it above removes it.
- **Negative path**: With nothing low, an explicit empty state renders ("all items above reorder point"); a clerk deep-linking the route is redirected/denied.

### Journey: J-13 — Deployed smoke oracle (docker compose)
- **Steps**: `docker compose up` from the repo root; wait for the db → backend → frontend healthchecks; load `/` in a browser.
- **Expected outcomes**: `[data-testid="app-ready"]` appears (SPA bootstrapped, not a 404 shell); the literal **`StockRoom`** is present in the rendered DOM in the unauthenticated state; `GET /api/health` through the nginx `/api` proxy returns `200`; a hard reload of a deep route such as `/items` returns the SPA via `try_files … /index.html` rather than an nginx 404. The backend entrypoint's `prisma migrate deploy` succeeds against an **empty** database before the API listens.
- **Negative path**: **None of `.colossus-acceptance.json`'s reject signatures may appear** — `home-title">Users<`, `Loading...`, `Failed to load users.` A blank/404 nginx root (wrong `dist/<project>/browser` copy path) fails this journey; so does a brand that only renders after an authenticated fetch resolves.

### Journey: J-14 — Admin configures runtime service credentials, then logs out
- **Steps**: Sign in as the admin → `/admin/settings` → observe one section per provisioned service (`postgresql`, `minio`) each with a configured/unconfigured badge → enter a credential → save → reload. Then use the header logout control.
- **Expected outcomes**: Save issues `PATCH /api/admin/settings`, the badge flips to configured, and the masked value survives a reload. No integration-credential sections are rendered (the spec declares no integrations). Logout clears the token from `localStorage` and redirects to `/login`; pressing Back does not restore an authenticated view, and a subsequent API call 401s and re-redirects to `/login`.
- **Negative path**: A clerk or non-admin manager deep-linking `/admin/settings` is redirected/denied and never sees credential fields. Session expiry mid-session (an API call returning 401) is caught by the auth interceptor and redirects to `/login` rather than showing a raw error.

## Data integrity tests

Invariants asserted directly against the database after each mutation.

- `DI-01` — **Stock is never negative.** After any sequence of movements, including the parallel-`OUT` storm in `API-MVC-25`, `SELECT min(qty) FROM "StockLevel" >= 0`. No code path may produce a negative row.
- `DI-02` — **Balance ≡ movement ledger.** For every `(itemId, locationId)`, `StockLevel.qty` equals `sum(IN + TRANSFER-in) - sum(OUT + TRANSFER-out)` replayed from the `Movement` table. Recomputing from the ledger must reproduce every stored balance exactly.
- `DI-03` — **Audit row and balance are atomic.** Every successful `POST /api/movements` writes exactly one `Movement` row; every rejected one (validation, insufficient stock) writes **zero** `Movement` rows and leaves all `StockLevel` rows byte-identical (full `$transaction` rollback).
- `DI-04` — **Transfers conserve total.** After a `TRANSFER`, `sum(qty)` across all locations for that item is unchanged from before; only the split moved.
- `DI-05` — **`(itemId, locationId)` uniqueness holds.** No duplicate `StockLevel` rows for a pair, even after concurrent first-time `IN` upserts (`API-MVC-26`); the `@@unique` constraint exists in the migration.
- `DI-06` — **SKU uniqueness holds.** `count(*) = count(distinct sku)` on `Item` after every duplicate-SKU attempt; a rejected create adds no row.
- `DI-07` — **Referential integrity on delete.** No `StockLevel` or `Movement` row is ever left pointing at a deleted `Item` or `Location`; any delete that would orphan history is refused with 409 instead of cascading.
- `DI-08` — **Every movement is attributed.** `Movement.userId` is non-null, references a real `User`, and equals the actor whose token made the request; `createdAt` is server-set and non-null (never client-supplied).
- `DI-09` — **Credentials are never stored or returned in plaintext.** `User.passwordHash` matches `^\$2[aby]\$10\$` for every row (bcrypt, cost 10); no API response body in the whole suite contains a `password` or `passwordHash` field.
- `DI-10` — **Seed is idempotent and consistent.** Running the seed twice yields the same row counts (2 demo users, 3 locations, 8 items) with no duplicates; opening stock is applied through the movement path so `DI-02` holds on a freshly seeded DB, and the low-stock report and at least one multi-location breakdown are **non-empty on first load**.
- `DI-11` — **Migration applies from empty.** `prisma migrate deploy` against a virgin Postgres 16 succeeds with no baseline, creates `Role`/`MovementType` enums and the `@@index([itemId])` / `@@index([createdAt])` indexes, and is re-runnable as a no-op.
- `DI-12` — **Build-chain identifiers agree.** The Angular project name, `angular.json` `outputPath`, the path copied in `frontend/Dockerfile`'s nginx stage, and `colossus.yaml`'s `outputDir` all reference the *same* `dist/<project>/browser` directory; `nginx.conf`'s `proxy_pass` port matches the backend's listening port and `colossus.yaml`'s declared backend port. A mismatch here fails J-13 with a confusing 404.
- `DI-13` — **Prisma stays on v6.** The committed lockfile resolves `prisma` and `@prisma/client` to `6.x` (not 7/8), and the schema keeps `generator client { provider = "prisma-client-js" }`, so the NestJS CommonJS build with decorator metadata compiles.

## Out of scope

- **The scaffolded tRPC surface** (`/trpc/users.findAll`, `/trpc/users.findById`, `ngx-trpc`, `src/app/trpc-client.types.ts`) — slated for deletion by `backend_agent`/`service_agent`. Not tested as behaviour; its *absence* is asserted only via the `surface.json` regeneration warning at the top of this file.
- **Movement edit / reversal / void.** The spec defines create + read only; correcting a mis-keyed movement has no defined path (`tasks.md` open question). No test asserts a compensating-movement workflow until that is decided.
- **Token revocation / server-side logout.** The spec explicitly makes logout a client-side token discard with no revocation list, so a token that is still within its 24 h `exp` continues to work after logout — this is documented behaviour, not a tested failure. (`API-LGN-09` pins it so nobody "fixes" it silently.)
- **Password-reset, email verification, account lockout, rate limiting, refresh tokens.** The spec is silent on all of them.
- **Password strength policy beyond presence/type.** No complexity rules are specified; only required/absent and type validation are tested.
- **minio / object storage behaviour.** Provisioned but unused — the spec declares no file-storage feature. Only the settings-page credential plumbing (`API-ADG-*`, `API-ADP-*`, J-14) is tested, never an upload/download path.
- **`MANAGER` role assignment.** `tasks.md` declares the enum value but no code path assigns it (first signup → `ADMIN`, later → `CLERK`). Tests target the *manager gate*, not the specific literal; if a distinct `MANAGER` is ever assigned, every manager-level case must be re-run under it.
- **Item `unit` vocabulary.** `unit` is a required free-text string with no allowed-value list in the spec; no enum validation is asserted.
- **Location `name` uniqueness.** No `@unique` in the schema, so duplicates are permitted (`API-LCC-07` records the behaviour rather than forbidding it).
- **Performance, load, and multi-tenant isolation.** No SLOs or tenancy model in the spec. The only concurrency assertion is the correctness fence in `API-MVC-25`.
- **Accessibility, i18n, responsive breakpoints, and visual regression.** The spec describes no design system, locale, or a11y target.
- **Demo credential hardening and open public signup.** Flagged in the spec's Risks as must-close-before-non-demo-exposure, but in-scope behaviour *for this build* is that they remain open — so no test asserts they are closed.
